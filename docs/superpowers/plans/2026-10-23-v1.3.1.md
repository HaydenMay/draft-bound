# Draftbound v1.3.1 Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` for native task-by-task implementation after the owner approves this plan. Track checklist steps and obtain one fresh whole-change review at the end. This document does not authorize implementation during the present planning-only turn.

**Goal:** Complete the requested legal/informational structure and visual polish while preserving the current game and every saved collection.

**Architecture:** Extend the existing Angular standalone components, hash navigation, SVG/Canvas assets and native CSS tokens. Keep palette identity separate from appearance and printed-card styling. Add small focused components where needed; do not replace the game shell, introduce a styling framework or migrate gameplay storage.

**Tech stack:** Angular 21.2.25, TypeScript, native CSS custom properties, SVG/Canvas, IndexedDB/localStorage, Vitest and Playwright; static GitHub Pages hosting.

**Source specification:** [Supplied master document, preserved unchanged](DRAFTBOUND_MASTER_PLAN_V1.3.1_V1.4.md), Part I §§1–26. Part II §§27–48 is future context only. [Repository audit](DRAFTBOUND_V1_3_1_AUDIT.md). [Preserved v1.4 decisions](DRAFTBOUND_V1_4_DESIGN_BACKLOG.md).

**Audited baseline:** local `main`, commit `cb86e1b1d1a5184430750874f0d11df3eda106f0`. This is the implemented v1.2 baseline, regardless of the new document's v1.3.1 release label. No intervening v1.3 functionality is assumed.

## Global constraints

- No recruiting, school, transfer, natural-potential, training, receiver-grade, professional-career, Hall of Fame or achievement-rule changes.
- Preserve four-game decisions, Quick/Full creation, RNG state, draft/career snapshots, stable IDs, favorites, ownership and unlocks. No storage clearing or collection regeneration.
- No real-team migration, official logos/photos, new collectible scene art, masking, card flipping or physical binder redesign.
- No advertising, analytics, accounts, subscriptions, payments, leaderboards, contact backend or new tracking services.
- Remove ornamental sheriff marks; preserve functional recruit/favorite stars. Change badge presentation without awarding new distinctions.
- Keep color literals in `src/colors.css`, college/team palettes in their existing data, and vectors in the shared authoritative catalog. No emoji or stock icon library.
- Preserve strong typography, the hero/card composition, intentional frame differences, keyboard access and reduced motion.
- Legal pages are drafts for appropriate owner/legal review. A disclaimer is not a license or a claim of legal compliance.
- Exact final semantic palette values must be validated; supplied source colors are not complete production token maps.

## Review focus

1. Old/unknown palette IDs must not reject an otherwise valid collection or overwrite unrelated settings. Pin this in Task 2's import/cache tests.
2. Previewing or dismissing the gallery must not silently save a palette; persistence errors must not falsely report success or lose keyboard focus. Pin this in Task 5.
3. A legal deep link, browser Back, or footer navigation during an active run must leave progress and RNG untouched—even when storage fails to load. Pin this in Tasks 6–7.
4. Legacy/new Draft/Career cards must share canonical logo/seal geometry and colors in DOM, thumbnails and PNG, independent of theme and saved school colors. Pin this in Task 3.
5. Star cleanup must preserve functional ratings/favorites, earned distinctions and locked position semantics rather than doing a global symbol replacement. Pin this in Tasks 3–4.

## Proposed decisions—not additional owner-approved requirements

| Topic | Recommended implementation | Reason / trade-off |

| Card logo | Fixed print-brand lettering and accent tokens in every card/export; school colors continue to identify the school elsewhere. | Removes the currently school-dependent logo arrow without recoloring art or altering saves. |

Alternative approaches considered: twelve large previews would make settings unwieldy; replacing the five current palettes would disrupt saved choices; immediate persistent preview would not protect the prior preference. A new router or generic policy CMS would add unnecessary architecture to this release.
