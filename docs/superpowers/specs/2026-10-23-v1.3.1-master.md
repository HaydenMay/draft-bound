# PART I — VERSION 1.3.1

# LEGAL & VISUAL POLISH

## 1. Mission

Draftbound is a browser-based football prospect-building roguelite.

Players construct a wide receiver using attributes inspired by real NFL receivers, develop that prospect through college, experience the NFL Draft, and optionally simulate a professional career.

Players collect Draft Edition and Career Edition cards representing their completed prospects.

The application already has a recognizable visual identity and functioning gameplay systems.

However, several previously requested interface changes remain incomplete.

Additionally, the application uses real NFL player names but does not currently have a sufficiently developed set of public-facing legal and informational pages.

Version 1.3.1 must address these issues.

### Primary objectives

1. Improve visual consistency throughout the application.
2. Remove unwanted decorative sheriff-star imagery.
3. Standardize shield-based branding and badges.
4. Fix inconsistent Draftbound logos on collectible cards.
5. Redesign the prospect creation position selector.
6. Correct the settings icon.
7. Introduce a scalable theme-selection interface.
8. Implement the previously researched color palettes.
9. Improve footer navigation.
10. Add appropriate legal and informational pages.
11. Preserve existing gameplay, progression, and saved data.
12. Verify the actual rendered application rather than relying exclusively on automated tests.

### Design philosophy

This is a **polish and completion release**, not a full redesign.

Preserve the existing application's strengths:

- Strong typography.
- Sports-card presentation.
- Warm, expressive visual identity.
- Readable game interfaces.
- Distinct collectible card treatments.
- Responsive browser-based gameplay.

Avoid unnecessary architectural changes.

Prefer reusable components, design tokens, and centralized configuration over duplicated implementations.

# 6. PROSPECT CREATION REDESIGN

## 6.1 Existing problem

The current prospect creator uses small position-selection controls that do not match the intended design.

The product owner previously requested a more prominent position-selection interface, but that request was not fully implemented.

This release must correct it.

## 6.2 Required design

Replace the current position-selection presentation with a **responsive grid of four equally sized position buttons**.

Positions:

- WR — Wide Receiver
- QB — Quarterback
- RB — Running Back
- TE — Tight End

All four tiles must have the same dimensions within the grid.

The design should be based on the previously supplied visual reference, but the requirements below are authoritative.

### Layout

Desktop:

```text
┌──────────────┬──────────────┐
│              │              │
│      WR      │      QB      │
│              │      🔒      │
│ WIDE RECEIVER│ QUARTERBACK  │
│              │              │
├──────────────┼──────────────┤
│              │              │
│      RB      │      TE      │
│              │      🔒      │
│ RUNNING BACK │  TIGHT END   │
│      🔒      │              │
└──────────────┴──────────────┘
```

The exact icon placement can be refined for visual balance.

The essential requirements are:

- Equal-sized tiles.
- Clear position abbreviations.
- Clear full position names.
- Consistent alignment.
- Responsive grid behavior.
- Locked states for unavailable positions.
- Strong selected state for WR.

### Wide Receiver

WR is currently the only playable position.

Its tile must:

- Be enabled.
- Be selected by default.
- Have a clear selected appearance.
- Respond appropriately to keyboard and pointer interaction.

### Quarterback, Running Back, Tight End

These positions are not currently playable.

Their tiles must:

- Be visibly locked.
- Display a recognizable lock icon.
- Remain disabled.
- Clearly communicate that they are unavailable.
- Not trigger incomplete gameplay flows.

Do not use radio-button circles to communicate locked positions.

Do not rely exclusively on muted colors.

### Equal-size requirement

**Every position tile must occupy an equal-sized cell in the display grid.**

Do not allow text length, icon size, or selected state to change the dimensions of individual buttons.

Use a consistent grid implementation rather than manually assigning independent widths.

### Responsive behavior

On desktop, use a balanced two-column grid.

On narrow screens, preserve readable labels and usable touch targets.

A single-column fallback is acceptable if necessary.

Avoid horizontal overflow.

### Accessibility

- Keyboard-accessible enabled controls.
- Correct disabled semantics.
- Visible focus indication.
- Accessible names.
- Clear locked-state communication.
- Sufficient contrast.

### Architecture

Implement the position selector in a way that supports unlocking additional positions later.

Do not hardcode the entire interface around WR-specific visual assumptions.

However, do not implement QB, RB, or TE gameplay.

### Preserve existing behavior

The redesign must not break:

- Prospect naming.
- Jersey number selection.
- Quick Mode.
- Full Mode.
- Prospect creation.
- Existing validation.
- Current navigation flow.

### Acceptance criteria

- Four equal-sized position tiles appear.
- WR is selected and functional.
- QB/RB/TE are locked.
- Lock icons replace the inappropriate radio-button presentation.
- Desktop and mobile layouts are verified.
- Existing creation flows continue working.

# 27. VERSION 1.4 VISION

Version 1.4 should transform the college portion of Draftbound into a deeper strategic development experience.

The central fantasy is:

**Build a unique wide receiver, choose where to develop, make difficult training decisions, earn better opportunities, and determine what kind of NFL prospect you become.**

The game should support different successful strategies.

Examples:

- A naturally gifted prospect who attends an elite school immediately.
- An overlooked recruit who earns major transfer offers.
- A loyal three-year player who maximizes natural potential.
- A late-transfer prospect who fixes a major weakness.
- A specialist who develops one exceptional attribute.
- An early declarant who gambles on draft position.
- A player who becomes an NFL star despite an unconventional college path.

Avoid making one route universally optimal.

The game must remain replayable and relatively short.

Depth should come from meaningful decisions, not excessive clicks.

# 28. NATURAL ATTRIBUTE POTENTIAL

## 28.1 Core distinction

Every attribute has two important values:

1. **Current ability**
2. **Natural potential**

These are not interchangeable.

Example:

| Attribute | Current | Natural potential |
|---|---:|---:|
| Speed | 74 | 96 |
| Route Running | 58 | 72 |
| Hands | 67 | 94 |

A player with 96 Speed potential does not automatically have 96 Speed.

The player must train to approach that potential.

This distinction is fundamental to the planned development system.

## 28.2 NFL source-player selections

The player selects attributes inspired by historical NFL receivers.

These selections primarily establish the prospect's potential profile.

The player must then develop those abilities through college.

This preserves the excitement of obtaining elite source traits without automatically creating a finished superstar.

## 28.3 Natural potential persistence

Natural potential should remain stable throughout the college career.

School programs may temporarily expand the available development ceiling.

However, the original natural potential remains unchanged.

This allows players to understand what their prospect could achieve naturally versus what specialized coaching makes possible.

## 29.1 Existing concern

The historical receiver database contains questionable attribute grades.

A Hall of Fame receiver should not feel like an unremarkable collection of A-tier attributes.

## 29.2 Planned direction

Audit the NFL receiver pool.

Every Hall of Fame receiver should possess at least one historically defensible S-tier trait.

This does not mean every attribute should be S-tier.

The goal is recognizable player identity.

Examples of meaningful specializations:

- Exceptional speed.
- Elite route running.
- Outstanding hands.
- Contested catching.
- Release ability.
- Yards after catch.

- Acceleration.

## 29.3 Specialists

The database should include more than all-time greats.

Include memorable specialists with exceptional individual strengths and legitimate weaknesses.

Previously discussed examples include:

- Tre Tucker as a speed-oriented source.
- Marquez Valdes-Scantling as a speed-oriented source with weaker hands.

These are design examples, not finalized attribute ratings.

## 29.4 S-tier rarity

Do not artificially suppress S-tier ratings merely to make them rare.

If a receiver was genuinely exceptional in a particular skill, represent that.

The challenge should come from:

- Random source availability.
- Attribute selection.
- Opportunity costs.
- Training budgets.
- Development ceilings.
- School choices.

Not from inaccurately downgrading historical players.

## 29.5 Separate Hall of Fame concepts

Historical NFL source-player ratings and fictional prospect Hall of Fame induction are separate systems.

A historical Hall of Famer having an S-tier trait does not mean the fictional prospect should automatically become a Hall of Famer.

Do not balance one system by distorting the other.

# 33. SCHOOL PRESTIGE AND SPECIALTY CEILINGS

## 33.1 Core mechanic

A school's specialty can increase the **available trainable ceiling** of its specialty attribute above the player's natural potential.

It does not instantly increase the attribute.

The player must spend training opportunities to realize the benefit.

## 33.2 Provisional prestige ceilings

| School prestige | Specialty ceiling |
|---|---:|
| Five stars | 99 |
| Four stars | 90 |
| Three stars | 85 |
| Two stars | 80 |
| One star | 75 |

These values are provisional.

They must be tested against the actual development economy.

## 33.3 Example

A player has:

- Route Running current: 65
- Route Running natural potential: 72

At a five-star Route Running school, the available ceiling may become 99.

But the player does not immediately jump to 99.

He must train Route Running.

If he spends his remaining college development opportunities elsewhere, the higher ceiling provides little benefit.

## 33.4 Permanent earned development

Suppose the player trains Route Running from 65 to 86 while attending the specialized school.

He then transfers away.

His natural potential remains 72.

However, his earned Route Running remains 86.

**Earned attributes never decrease simply because a player transfers.**

The new school may no longer provide access to the same expanded ceiling.

Therefore, the player may be unable to train Route Running higher unless the new school's specialty or another applicable mechanic permits it.

## 33.5 Specialty acceleration

Schools should also accelerate development of their specialty attribute.

The exact multiplier is not finalized.

The acceleration must interact with:

- Training choices.
- Development efficiency.
- Diminishing returns.
- Attribute ceilings.

The result should be a meaningful advantage, not guaranteed maximum ratings.

# 34. TRANSFER STRATEGY

The goal is to create legitimate strategic tension between staying and transferring.

## 34.1 Staying

Advantages:

- Greater continuity.
- Better development efficiency.
- More opportunity to realize existing potential.
- Less disruption to training.

## 34.2 Transferring

Advantages:

- New school specialties.
- Higher ceilings in previously limited attributes.
- Potentially stronger coaching.
- New development opportunities.

Costs:

- Reduced continuity.
- Less efficient training.
- Limited remaining college seasons.

## 34.3 Desired late-transfer example

A player enters junior year with:

- Speed 91 / 96
- Acceleration 88 / 93
- Hands 89 / 96
- Route Running 68 / 72
- Release 85 / 90

Most attributes are approaching natural potential.

Route Running has a low natural ceiling.

Transferring to an elite Route Running school may be the obvious choice.

That is desirable.

The player can sacrifice some efficiency in exchange for access to a much higher Route Running ceiling.

## 34.4 Alternative example

Another player enters junior year with several attributes still 20 points below their natural potential.

That player may benefit more from staying at the current school.

Continuity could help develop multiple existing strengths.

The goal is for both decisions to make sense depending on the prospect.

# 35. DEVELOPMENT CONTINUITY

## 35.1 Confirmed provisional targets

The owner approved the following development-efficiency targets:

| College path | Freshman | Sophomore | Junior |
|---|---:|---:|---:|
| A → A → A | 100% | 95% | 90% |
| A → B → B | 100% | 85% | 80% |
| A → A → B | 100% | 95% | 75% |
| A → B → C | 100% | 85% | 65% |

These percentages represent development efficiency, not direct attribute ratings.

## 35.2 Interpretation

### A → A → A

The player stays at one school for all three years.

This produces the best continuity.

### A → B → B

The player transfers after freshman year, then stays at the new school.

Junior-year efficiency improves because the player has established continuity at the destination.

### A → A → B

The player stays for two seasons, then transfers before junior year.

He benefits from a strong sophomore season but receives lower junior-year efficiency because he must adapt to a new program.

The owner specifically preferred **75%** here.

A previous 65% proposal was considered excessively harsh.

### A → B → C

The player transfers every year.

He receives the lowest junior-year efficiency but potentially accesses multiple school specialties.

## 35.3 Combined efficiency

Assuming equal baseline training opportunities each year:

| Path | Combined efficiency |
|---|---:|
| A → A → A | 285% |
| A → B → B | 265% |
| A → A → B | 270% |
| A → B → C | 250% |

These totals do not include school specialty bonuses or other development modifiers.

## 35.4 Implementation principle

Do not hardcode individual school names into the continuity calculation.

Calculate development efficiency from school history and year.

The exact internal formula is not finalized.

It should produce the approved target outcomes and remain extensible.

Avoid arbitrary permanent transfer penalties.

Avoid a moralized loyalty system.

The goal is to reward developmental stability.

## 36.2 Desired outcomes

- Respect current and potential ratings.
- Interact with school specialties.
- Interact with continuity.
- Avoid automatic perfect builds.
- Remain fast to use.
- Avoid unnecessary repetitive clicking.

## 36.3 Training cadence — unresolved

Two approaches were discussed.

### Option A: Weekly training choices

Players choose training after each game.

Advantages:

- Immediate feedback.
- Frequent strategic adjustments.
- Strong connection to weekly performance.

Disadvantages:

- More clicks.
- Greater repetition.
- Potentially slower runs.

### Option B: Persistent training plans

Players choose a default training plan.

That plan continues automatically until changed.

The game displays weekly growth and allows adjustments.

Advantages:

- Less repetitive input.
- Better pacing.
- Still supports strategy.
- Integrates naturally with weekly broadcasts.

Disadvantages:

- Could become too passive.
- Requires clear feedback and easy adjustment.

**No final decision has been made.**

The owner sees merit in both.

A hybrid system may be appropriate.

Do not finalize this without reviewing current gameplay and playtest feedback.
