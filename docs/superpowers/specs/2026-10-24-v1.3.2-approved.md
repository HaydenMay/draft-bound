## 2. Priority 0 — Save integrity and v1.4 compatibility baseline

**Intent:** Existing local collections must survive v1.3.2 and provide trustworthy fixtures for the imminent v1.4 migration work.

### 2.1 Investigate and safely handle the 1,000-entry binder cap

During review, `src/app/persistence/save.ts` validated `entries` with an upper bound of **1,000**. The normal completion path in `src/app/domain/engine.ts` / `src/app/application/game-store.ts` appeared able to append a newly drafted entry without checking that the cap had been reached. If so, the 1,001st entry could be written to IndexedDB and then rejected on the next reload, making the entire collection appear unreadable.

**Verify this exact path in the current code** rather than assuming it persists. Then implement a **small, safe safeguard** against writing a collection beyond the supported cap.

Preferred behavior, unless current architecture provides a clearly safer approach:

1. Centralize the supported binder-entry limit so save validation and gameplay write paths cannot disagree.
2. Prevent starting a **new** prospect when the binder has reached that cap, with a clear, nontechnical message and an immediate option/instruction to **export the existing collection**. Do not imply that export frees storage or increases the cap.
3. Add a **defense-in-depth guard** at the actual point where a completed Draft Edition entry is appended. This must protect against an unusual imported/legacy state with an active run and a full binder. Do **not** save an invalid 1,001-entry envelope, silently drop an old card, clear the active run, or pretend draft completion succeeded.
4. If the fallback guard triggers, leave the last valid persisted collection intact, retain/recover the in-memory active state where practical, display a comprehensible explanation, and make backup export available. Avoid a dead-end UI or an inescapable save corruption state.
5. Keep import validation explicit: supported collections load normally; a file over the supported entry count should fail **before replacement** with a useful reason, leaving the current save unchanged.
6. Do **not** solve this by merely raising `1000` to an arbitrary larger number. Discuss a future scalable limit separately if warranted; this release needs a controlled boundary, not unverified capacity expansion.

**Required tests:** 999-entry completion reaches 1,000 and reloads; at-limit fresh-run action is safely blocked; active-run-at-limit fallback never persists 1,001; import of 1,001 entries is rejected without overwriting the current collection; normal and error-path backup exports remain intact. Optimize test fixtures to avoid massive browser runtimes.

### 2.2 Freeze reproducible v1.3.1-format fixtures

Add small, deterministic, **synthetic** fixtures (or test helpers producing them) representative of valid saves from the current release. Cover at least:

- A partially completed **Quick** prospect.
- A partially completed **Full** prospect.
- A completed Draft Edition entry; a separate entry with a saved Career Edition.
- Earned cosmetic frames/unlocks, favorites, saved card customizations, appearance/theme preferences.
- Archived/historical entry presentation if supported by the present validator.
- At least one file exported through the public backup flow and re-imported through validation.

Tests should establish that v1.3.2:

- Reads and renders the fixtures without data loss.
- Preserves existing `creationMode` and random state when resuming an old active prospect.
- Does not rewrite already-completed draft results, team/school snapshots, statistics, card scenes, achievements, or cosmetic ownership.
- Still supports export, import preview, prior-save backup on replacement, cross-tab safety, and unsupported-save recovery behavior.

These fixtures are **future v1.4 migration baselines**, not permission to create a new v1.4 data model now. Document their location and purpose. Do not commit personally identifying real-user backups.

### 2.3 Check failure-path state consistency

Specifically inspect how the app handles a failed `persist()` after a domain transition. Verify whether the interface can show progressed state that hasn't actually been written (the app already warns about unsaved progress). Ensure the 1,000-entry fix doesn't worsen this behavior. Add an appropriate regression around a failed write at the collection boundary. **Do not undertake a large transactional rewrite** unless tests reveal an actual high-severity data-integrity flaw; flag larger changes for separate approval.

**Acceptance:** No new save corruption path at the entry limit; existing saves and saved outcomes remain intact; fixtures can later be reused for v1.4.

## 3. Priority 1 — Prospect creator: Full by default, clearer mode choice

### 3.1 Change the default to Full

The new-prospect form currently initialized `creationMode` to `'quick'` in `src/app/app.ts` at the time of audit. Change the initial mode for newly created prospects to **`'full'`**.

- On a fresh visit, **Full is selected** in the New Prospect dialog.
- **Each time the player begins a fresh new-prospect flow, preselect Full**, including after previously creating a Quick prospect in the same browser session. Do not reset the selection in the middle of an open form or overwrite a resumed run. No persisted creation-mode preference was observed at audit; do not introduce one for this release.
- The player can switch to **Quick**, and starting that run genuinely uses Quick.
- A newly started Full run persists `creationMode: 'full'`; its potential selection requires all **eight manual selections** in addition to the natural S-tier gift.
- A newly started Quick run persists `creationMode: 'quick'`; it still uses **three manual selections**, with the remaining potentials auto-filled as before.
- Resuming an existing Quick run stays Quick. Resuming an existing Full run stays Full. Do not apply the new default retroactively to saved runs or historical cards.
- **Do not change** `createRun(...)`'s exported default argument or domain-level behavior solely to accomplish a UI default unless tests demonstrate it is the correct and backward-compatible solution. Prefer the form's explicit mode choice.

### 3.2 Make the choice self-explanatory

Players currently see short **Quick / Full** labels with no immediate explanation of their different selection counts. Improve the two equal, accessible option labels with concise text such as:

- **Full · 8 picks** (default)
- **Quick · 3 picks**

Use clear accessible names; a concise one-line description or native accessible description may be added **only if needed** for users to understand that the counts refer to manual trait/potential selections. **Do not** clutter the modal with long instructions. Ensure the counts are not mistaken for the total number of traits (the natural gift is separate). Both choices must remain keyboard-usable and visibly selected.

Keep the existing editable/generated name, jersey number, four equal position tiles, lock states, and Create button layout. Never make QB/RB/TE playable as part of this work.

**Acceptance/tests:** Fresh UI defaults to Full; selecting Quick works; mode controls are labeled and accessible; start/resume/reload for both modes; no changes to generated source offers or probabilities; creation modal still fits mobile widths.

## 4. Priority 1 — Mobile form legibility and Safari focus behavior

Review **interactive editable controls**, especially at 320, 375, and 390 CSS-pixel viewport widths. At audit time, several inputs/selects were styled around **10–12px**, which can cause iOS Safari to zoom unexpectedly on focus and is uncomfortable for touch use.

Candidate locations to inspect:

- New Prospect: name and jersey number.
- Binder: search and filter/sort selects.
- College training: focused/intensive attribute selector.
- Settings: appearance selector and import-related editable controls.
- Contact: future-ready form controls, where present.

**Requirements:**

1. Set focused/editable mobile inputs and selects to **at least 16 CSS pixels** where needed to prevent iOS auto-zoom; verify computed style in final production CSS at the target viewport sizes. Keep labels/help text visually consistent without unnecessarily enlarging unrelated game/card typography.
2. Preserve comfortable tap targets, native keyboard behavior, focus rings, zoom/accessibility, and existing dropdown chevrons across light/dark themes.
3. Check no input is clipped by its container, causes horizontal page overflow, hides a submit button behind the keyboard without scroll access, or disrupts the creator modal's 2×2 locked-position layout.
4. Do not disable user zoom (`user-scalable=no` / restrictive viewport settings) as a workaround.
5. Use actual Safari/iPhone verification if available; otherwise explicitly label browser automation as **emulation** and call out device-only behavior as not independently verified.

**Acceptance/tests:** computed editable font size is >=16px on the relevant small breakpoints, mobile modal/filters remain usable, no 320px horizontal overflow, and the palette/theme switch still renders correctly.

## 5. Priority 1 — Coaching intervention explanation matches actual rules

At audit time `src/app/domain/engine.ts` applied the coach-prescribed intensive focus **to the first game of the next four-game block**, then used the player's chosen plan for the following three games. However, a training-screen message read approximately:

> “Next block requires intensive [attribute] work.”

This incorrectly suggests **all four games** are overridden.

**Requirements:**

- Verify the current `train` implementation and update the player-facing explanation to match it. Proposed succinct wording: **“Coach's focus applies to the next game. Your selected plan resumes afterward.”**
- Make clear, if displayed, that choosing an already-compliant Intensive plan is recognized rather than being mysteriously overridden.
- Check the recap's `already_compliant` / `substituted` messaging for consistency with the first-game-only intervention.
- **No** changes to coaching triggers, priority, per-type-per-season limit, plan replacement, growth coefficients, random number consumption, or training progression.

**Acceptance/tests:** copy accurately describes the first game; both compliance paths still work; four-game simulations and save/reload are unchanged.
